Workloads

Three shapes, not one card

The card benchmarks measure fill cost, which says little about what people actually render. These three stress different stages and report each stage separately, so the split can move between workloads. Same machine, 1200×630, criterion 95% CI — reproduce with cargo bench -p hikari-rs --bench render.

Choosing an output format

Encoding is a decision, and it matters more than any of the timings above

PathTimeFlat card12 image tiles
render_svg — serialises, rasterises nothing0.005 ms309 Bn/a
render_placed_to_rgba — stops at the pixels1.89 ms——
render_webp~3.5 ms8,662 B178,902 B
render_png~3.8 ms12,238 B28,858 B

Three things follow, and none of them is "always use WebP". If the consumer takes vectors, render_svg is 780× faster because it rasterises nothing. If it needs pixels and the content is flat UI work, lossless WebP wins ~29% on size — and on photographic or high-frequency content it loses by 6.2×, because PNG's predictive filters have a different enemy than WebP's palette. There is no default that is right; it is a measurement on your own content.

PNG encoder

The trade-off curve

Encoder settings trade bytes against time. The rejected rows are recorded so the choice is reproducible rather than asserted.

SettingBytesTime
tiny-skia default 117,7602.3 ms superseded
Best + Adaptive ~44,000~300 ms rejected — 100× slower for 1 KB
Default + Adaptive + RGB-strip 43,100~10.5 ms shipped
Fast + Adaptive 74,081~3.9 ms rejected — size

A filter-trial experiment, trying every filter at two levels, floors out around 44 KB on these pixels, so the remaining gap is content-side — gradient smoothness and anti-aliasing — not encoder-side. The trial was rejected: all cost, no gain.

Determinism

Same bytes, every platform

This is the property that makes golden-image testing possible for anyone downstream, so it is gated in CI. The expected digests live in crates/hikari/tests/determinism.sha256 and the render fails the build if it drifts.

TargetPNGSVG
macOS ARM64 21,649 B738 B
Linux x86_64 21,649 B738 B

These digests changed in v0.18, and the old ones were wrong. The embedded font subset was dropping GSUB, GPOS and GDEF, and the paint path was looking glyphs up by source character instead of by the id the shaper chose. Kerning and ligatures now actually apply, so glyph positions moved and the bytes moved with them.

Corrections

Where this document has been wrong

Kept deliberately. A benchmark document that has never been wrong has probably not been measuring anything.

v0.7
Claimed a large speed advantage. It came from a debug build with weak compression. Withdrawn; the numbers here are release numbers.
v0.13
Recorded a “kerning/ligature tradeoff” as an accepted cost of font subsetting. It was not a tradeoff — the subsetter was dropping the layout tables, so both were silently absent. Fixed in v0.18.
v0.18
Corrected the determinism digests, for the reason above.
v0.21.11 — 300× layout cost
image_dimensions fully decoded every image to read dimensions that live in the header. Layout went 3.969 ms → 0.013 ms and paint → 8.9 ms once the second decode went away. It was never found by any test or corpus case, because nothing was wrong with the output — it is a performance defect that looks exactly like a non-defect. Found by the image workload bench on the first run it existed.
v0.21.11 — three retractions
"51% of render is zlib" → 40–56% by workload. "WebP is a 29% size win" → 29% smaller on flat cards and 6.2× larger on image tiles. "Cold start is dominated by glyph rasterisation" → ~0.9 ms of 10.4 ms. All three were the same mistake in different clothes: measuring one thing and writing the answer down as though it were general.

Still to improve

Known weak spots

Cold start
Roughly a tenth of it is glyph rasterisation, measured; the rest is one-time font parse, pixmap allocation and encode. Pre-warming was measured and rejected. Closed as not worth doing; the reasoning stays on record.
Card output size
Examined in v0.21.10: the banding hypothesis was wrong. The gradient is constant down each column and its largest step is 1, so 57 KB is what a smooth gradient costs to compress losslessly, with about 3.7% of encoder headroom not worth taking. Answered; closed.
Workload coverage
Resolved in v0.21.11 — the text-dense, image and document workloads above exist now, and their first run found the 300× layout defect. What remains open: benchmarking on a second machine class (Linux x86_64), which is where the CI perf gate runs.
